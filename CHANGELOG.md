# Changelog

All notable changes to **NGql.Core** and its companion `dotnet-ngql` CLI are recorded here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and this project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Per-release deep-dive notes live under [`docs/<version>/RELEASE_NOTES.md`](docs/) when they exist; this file is the terse summary intended for upgrade decisions.

The companion Claude Code Skill is versioned independently — see [`.claude/skills/ngql-local/CHANGELOG.md`](.claude/skills/ngql-local/CHANGELOG.md).

## [2.2.1] - 2026-09-24

Release notes: [`docs/v2.2.1/RELEASE_NOTES.md`](docs/v2.2.1/RELEASE_NOTES.md).

### Deprecated
- The classic API — `Query`, `Mutation` and `QueryBlock` — is marked `[Obsolete]` with diagnostic ID `NGQL0001` and will be removed in NGql 3.0. It keeps working unchanged in 2.x. Builds that treat warnings as errors can suppress just this ID (`<NoWarn>$(NoWarn);NGQL0001</NoWarn>`) while migrating to `QueryBuilder.CreateDefaultBuilder` / `CreateMutationBuilder`; see the [migration guide](docs/reference/MIGRATION.md).

### Changed
- Every workload in the release benchmark allocates less than 2.2.0; none allocates more. No public signature, rendered output or collection-sharing behavior changed. Managed bytes per operation, .NET 9, 2.2.0 → 2.2.1: simple query 1,413 → 1,034 (−27%); dictionary arguments ×50 185,999 → 126,802 (−32%); directives ×50 210,002 → 138,404 (−34%); classic 10-level nesting 13,363 → 6,001 (−55%); building 100 queries 204,001 → 160,000 (−22%); 200 dotted paths 232,059 → 202,988 (−12.5%). In the in-process job, 21 of the 30 workloads are faster with non-overlapping confidence intervals and none is slower (simple query −34%, directives ×50 −32%, dictionary arguments ×50 −24%). Full tables: [`docs/v2.2.1/BENCHMARKS.md`](docs/v2.2.1/BENCHMARKS.md).
- Adding many root fields with a lambda or with arguments is linear rather than quadratic: 1,000 roots with a lambda take 0.13 ms instead of 1.54 ms, and 1,000 roots with arguments 0.25 ms instead of 2.09 ms.

### Fixed
- A root field added with a lambda or with arguments was matched against existing roots case-sensitively, while the root dictionary is case-insensitive. `AddField("User", …)` followed by `AddField("user", …)` therefore replaced the first field and silently dropped its children. The second call now merges into the existing root, as nested fields already did.

## [2.2.0] - 2026-09-20

### Added
- `QueryBuilder.CreateSubscriptionBuilder(name)` and `CreateSubscriptionBuilder(name, MergingStrategy)` — completes the query/mutation/subscription trio on the fluent builder. The surface (`AddField`, `Include`, `WithMetadata`, merging) is identical to the query and mutation paths; only the leading operation keyword differs, rendering as `subscription Name(...) { … }`. New `OperationType.Subscription` backs the render.
- **Named fragment support** via `QueryBuilder.AddFragment(name, onType, build)` + `FieldBuilder.SpreadFragment(name)`. Renders as `fragment Name on TypeName { … }` after the operation block (sorted alphabetically by name), with `...Name` spreads emitted at each use site (declaration order preserved). Spreads work inside fields, inline fragments, and other named fragments. New `InlineFragmentDefinition.SpreadFragments` and `NamedFragmentDefinition.SpreadFragments` properties expose the data model. Closes [#20](https://github.com/dolifer/NGql/issues/20). Public API additions: `QueryBuilder.AddFragment`, `FieldBuilder.SpreadFragment`, `QueryDefinition.NamedFragments`, `FieldDefinition.SpreadFragments`, `Abstractions.NamedFragmentDefinition`.
- **Field directive support** via `FieldBuilder.IncludeIf(condition)`, `FieldBuilder.SkipIf(condition)`, and the generic `FieldBuilder.Directive(name, arguments)`. Directives render after a field's name and arguments and before its selection set, space-separated in insertion order: `field(args) @include(if:$x) @skip(if:$y) { … }`. `IncludeIf`/`SkipIf` have two overloads: passing a `Variable` (matching [#23](https://github.com/dolifer/NGql/issues/23)'s proposed API) both renders the directive and **auto-promotes the variable into the operation signature** — deduplicated with any other variable of the same name — exactly like a `Variable` passed as a field argument does today; the `Variable`'s type must reduce to `Boolean`/`Boolean!` or the call throws. Passing a bare `string` renders the directive with a `$name` reference but does **not** declare it — use that overload only when the variable is already declared some other way (e.g. another field argument, or `QueryBuilder.Definition.Variables.Add(...)`), since a `string` carries no GraphQL type to promote from. `Directive` accepts the name with or without a leading `@` (normalized, stored without) and promotes any `Variable` values found in its arguments dictionary the same way. Directive arguments reuse the same value formatter as field arguments. Directive-less fields are unaffected — the backing store stays null, so there is zero added allocation. `OnType`'s lambda supports the same `IncludeIf`/`SkipIf`/`Directive` methods, attaching to the inline fragment itself: `... on Admin @include(if:$x){ … }`. Calling `IncludeIf`/`SkipIf` (or `Directive` with the literal name `"include"`/`"skip"`) twice on the same field or fragment is **last-call-wins** — the later condition replaces the earlier one in place rather than appending a second occurrence, since `@include`/`@skip` are non-repeatable per the GraphQL spec (§5.7.3) and two on one location is invalid GraphQL. Custom directives keep their existing append/dedup-by-structural-equality behavior — only the two reserved conditional names are collapsed. `MergingStrategy.MergeByFieldPath` now treats a field's `@include`/`@skip` state as part of its merge identity: two fragments requesting the same path under *different* conditions no longer collapse into one node with both directives attached (which would silently apply one side's condition to the other side's content) — they auto-alias into separate roots, exactly like an argument conflict does today; same condition (or no condition on either side) still merges normally. `PreservationBuilder` carries a preserved field's directives — and any variable they reference — into the projected query, whether the directive sits on the preserved leaf or an ancestor on the preserved path. Public API additions: `FieldBuilder.IncludeIf`, `FieldBuilder.SkipIf`, `FieldBuilder.Directive`, `FieldDefinition.Directives`, `FieldDefinition.HasDirectives`, `InlineFragmentDefinition.Directives`, `InlineFragmentDefinition.HasDirectives`, `Abstractions.FieldDirective`. Closes [#23](https://github.com/dolifer/NGql/issues/23).
- **Fragment-aware `QueryBuilder.Include`** — merging a fragment-bearing query now produces valid GraphQL instead of throwing. Named-fragment definitions carry over using the existing `AddFragment` collision semantics (same name + same type dedupes and merges the fragment body; same name + a conflicting type throws `InvalidOperationException`), transitively pulling in fragments those bodies spread. A merged field keeps its inline fragments (`... on T { … }`, merged by type name when both sides select the same field), its fragment spreads (`...Name`, insertion order preserved, duplicates skipped), and its directives. All fragment state is deep-cloned, so mutating the source query after `Include` never affects the merged result. Completes the fragment-aware `Include` follow-up to [#20](https://github.com/dolifer/NGql/issues/20).
- `FieldDefinition.HasMetadata` — allocation-free check for metadata presence. Reading the `Metadata` getter materializes (and permanently attaches) an empty dictionary on metadata-less fields; use `HasMetadata` as the guard when scanning large field trees.
- **`AppendTo(StringBuilder)` and `WriteTo(TextWriter)`** on `QueryBuilder`, `Query`, and `Mutation` — render a query into an existing buffer or stream without the terminal `ToString()` string allocation. Output is byte-identical to `ToString()`; content is copied chunk-wise (`StringBuilder.Append(StringBuilder)` / `GetChunks()`), so no intermediate string is materialized. Reusing a `StringBuilder` across renders cuts allocation by ~40–65% versus `ToString()` per call.
- **`WriteUtf8(IBufferWriter<byte>)`** on `QueryBuilder`, `Query`, and `Mutation` — transcode the rendered GraphQL directly to UTF-8 into a caller-supplied buffer (e.g. `PipeWriter`, `ArrayBufferWriter<byte>`, a Kestrel response body) with no intermediate `string` and no intermediate `byte[]`. Bytes are identical to `Encoding.UTF8.GetBytes(query.ToString())` — including astral codepoints/emoji, which a stateful encoder reassembles correctly across chunk boundaries. Writing into a reused buffer cuts allocation ~51–71% versus the `ToString()` + `Encoding.UTF8.GetBytes` path.
- `PreservationBuilder.PreserveAtPathInRoot(fieldPath, nodePath, root)` — scopes preservation to exactly one named query root. `PreserveAtPath` resolves `nodePath` relative to *every* root, which is ambiguous when several roots share a node name; the new overload matches `root` against each root's alias-or-name (ordinal, case-insensitive) and never falls back. If `root` names no existing root, or `nodePath` does not resolve beneath it, the call is a clean no-op — it never retargets a different root.

### Changed
- **Breaking (minor):** `QueryDefinition.Fields` and `QueryDefinition.Metadata` now return `IReadOnlyDictionary<,>` instead of the live mutable `Dictionary<,>`, and the `Metadata` public setter has been removed. Consumers could previously `Clear()`/`Remove()`/insert into these dictionaries and desync the internal query map. Read access (indexer-get, `ContainsKey`, `TryGetValue`, `Count`, `Values`, enumeration) is unchanged; mutate via the `QueryBuilder`/`FieldBuilder` API. Mirrors the existing `NamedFragments` encapsulation.
- **Merging is now linear rather than quadratic.** Batches that share a field path but carry divergent argument filters — the shape produced by composing many independent query fragments into one request — previously cost O(N²) in both time and allocation, because every `Include` rescanned all existing roots and ran a full structural comparison against each. Merge candidates are now indexed by field name and sub-bucketed by a conservative deep-argument fingerprint, so an incoming fragment goes straight to the candidates that could actually merge. Measured on 800 divergent-filter fragments: ~117 ms → ~1.4 ms and ~60 MB → ~1.5 MB, with structural comparisons dropping from ~320,000 to zero. Shared-parent merges (many fragments collapsing into one node) are linear too, via index-backed child lookup and unique-key generation. Rendered output is unchanged in every case — this is purely a lookup optimisation, and the full structural comparison still decides every merge.
- Classic `Query`/`Mutation` deep nesting: rendering no longer materializes an intermediate string per nested block. A 30-level nested query renders 4.0× faster with 12.1× less allocation than 2.1.0 (39.26 → 9.86 µs, 685,332 → 56,556 B); a 10-level one 2.2× faster with 4.1× less allocation.
- Performance: assorted allocation cuts across the builder, render, and preservation hot paths (LINQ-free render/insert loops, comparer-based hashing, span-based alias parsing, pooled path building, pre-sized clone collections).
- **Allocation pass across construction, rendering and merging.** Every workload in the shared release benchmark allocates less than 2.1.0 — none more. Representative figures (managed bytes per operation, .NET 9, 2.1.0 → 2.2.0): simple query 1,597 → 1,413; complex query with merging 6,380 → 4,721 (−26%); 200 dotted paths 236,984 → 232,059; 500-field flat selection 129,444 → 129,280; dictionary arguments ×50 208,804 → 185,999; `ToString` ×50 42,015 → 32,195; expression preservation ×50 180,879 → 147,528. In the in-process benchmark job, 22 of the 24 workloads are also faster than 2.1.0 with non-overlapping confidence intervals — typically 9–22% (simple query −11%, complex merging −15%, `ToString` ×50 −22%); large flat selections are unchanged. Retained heap for a held merged query falls from 3,008 to 2,352 B. Full tables: [`docs/v2.2.0/BENCHMARKS.md`](docs/v2.2.0/BENCHMARKS.md); method and known costs: [`docs/PERFORMANCE_REVIEW.md` at 2.2.0](https://github.com/dolifer/NGql/blob/2.2.0/docs/PERFORMANCE_REVIEW.md).
- Rendering no longer allocates for the common small cases: scalars, decimals and dates format into a stack buffer under the invariant culture; a lone argument or variable renders without an enumerator (208 → 80 B, and a warm write to a sink allocates nothing); sorted field rendering to a sink allocates nothing; root arguments sort pooled entries instead of building a dictionary (1,000 arguments: 92,497 → 36,024 B).
- Inserting arguments one at a time is linear: 1,000 individual `AddArgument`/`Where` calls drop from about 4.2 ms and 240 KB to about 0.4 ms and 56 KB. 1,000 root variables drop from 294 KB to 54 KB.
- `FieldDefinition` is back to 96 B per instance (it had grown to 144 B with directives, fragments and merge fingerprints): fragments, spreads, directives and metadata share one optional holder that plain fields never allocate. Fields that do carry them pay a 48 B holder; cold builds of metadata-bearing fields are about 12% slower as a result.
- Merge-index invalidation is scoped to the queries that observe a field instead of being process-wide, so mutating one query no longer forces unrelated queries to rebuild their merge buckets (merge after an unrelated mutation with 1,000 candidates: 81.6 µs / 269 KB → 0.29 µs / 296 B).
- Bounded retention: the per-thread render-builder pool keeps at most 262,144 characters in total (previously per builder, up to 4×); custom type names are cached in two lock-free generations of 2,048, so names still in use survive churn and a miss never takes a global lock; reflection metadata caches hold types weakly, so collectible assemblies can unload.
- **Breaking (behavior):** signed integers always render with the ASCII minus sign regardless of `CultureInfo.CurrentCulture`; previously a culture with a custom negative sign produced invalid GraphQL. This costs about 4 ns per integer.
- Interned type-name strings are no longer guaranteed to be the same instance for the life of the process (the cache is bounded); string equality is unaffected.

### Fixed
- **Same-name/different-alias sibling fields no longer overwrite each other.** Adding `aliasA:id` and `aliasB:id` under one parent and then re-referencing either — through `Include`, a second `AddField`, or a nested builder action — replaced the wrong sibling, silently destroying one field and emitting a duplicate response key that a GraphQL server rejects (`user{ aliasB:id aliasB:id }`). Field identity on the merge path is now the GraphQL response key (`alias ?? name`) rather than the name alone, and replacement targets the matched child by reference. Present in 2.1.0 and earlier.
- **`AddArgument(IReadOnlyDictionary)` is now atomic.** A key colliding only by case threw partway through, leaving earlier entries applied and — when a value was a `Variable` — an orphaned variable declared in the operation signature but referenced by no argument, which servers reject as "variable is never used". Every entry is now validated and transformed before any is committed, so a rejected call leaves the block untouched. The single-key overload was made atomic in the same way.
- **`NullReferenceException` when merging into a childless object-typed field.** A field given an explicit object type via `AddField(name, type)` without sub-fields kept a null child store; merging an incoming field that *did* have children dereferenced it. Genuine type conflicts still throw `QueryMergeException` as before.
- Merge-index invalidation gaps that could silently drop a legitimate merge and emit a spurious aliased root instead. Mutating a field's arguments outside the merge path — a retained nested `FieldBuilder`, a root-level `AddField` widening arguments, or a `MergeByDefault` include of a leaf — left the field indexed under its previous shape. All such mutation sites now invalidate correctly.
- `PreservationBuilder.Build()` projections are now fully isolated from the source builder. Previously the preserved query shared `FieldDefinition` subtrees (and intermediate argument dictionaries) with the source, so mutating either builder after `Build()` silently leaked into the other — including new fields appearing in already-issued role-based projections. Preserved trees are deep-cloned, keep inline fragments and fragment spreads, and carry over the named-fragment definitions they reference (transitively; unreferenced definitions are not emitted).
- Merge-index invalidation, continued (affects 2.2.0 previews only — the index is new in 2.2.0): mutating an already-indexed query through a captured `FieldBuilder` — `Where`, `IncludeIf`/`SkipIf`, or an argument-bearing `AddField`, on a builder captured from a nested action, from a dotted path (`AddField("a.b", args, b => captured = b)`) or after a sub-field overload — left the ancestors' fingerprints stale, so the next matching `Include` produced a spurious aliased root (`metrics_1`) instead of merging.
- `WriteUtf8` (new in 2.2.0; affects previews only) threw `ArgumentException` when the `IBufferWriter<byte>` returned a span shorter than requested, as bounded or slab-capped writers do. Single-chunk output now falls back to the chunked encoder.
- `dotnet-ngql`: `ngql -` (read the snippet from stdin), documented since 2.1, never worked — the CLI parser rejected the bare `-` with exit code 64. It now reads stdin as documented.

## [2.1.0] - 2026-05-04

### Added
- **Inline fragment support** via `FieldBuilder.OnType("TypeName", b => …)`. Renders as `... on TypeName { … }` after the field's plain children, sorted alphabetically by type name. Multiple `OnType` calls for the same type on the same parent merge into one combined fragment definition. Nested fragments (fragment-inside-fragment) work recursively. Solves union/interface narrowing for queries like GitHub's `search.nodes`. New `InlineFragmentDefinition` record exposes the data model. Public API additions: `FieldBuilder.OnType`, `FieldDefinition.InlineFragments`, `FieldDefinition.HasInlineFragments`, `Abstractions.InlineFragmentDefinition`. Named fragments (`fragment X on T { … }` + `...X` spreads) remain unsupported — tracked in [issue #20](https://github.com/dolifer/NGql/issues/20).
- `QueryBuilder.CreateMutationBuilder(name)` and `CreateMutationBuilder(name, MergingStrategy)` — the fluent builder now produces both queries and mutations from the same surface, removing the need to drop down to the classic `Mutation` type for new code.
- `QueryBuilder.AddField` gains `(field, args, lambda)` and `(field, subFields, lambda)` shorthand overloads, eliminating the `metadata: null` boilerplate previously required for these shapes.
- `FieldBuilder.AddField` gains args-first variants (`(field, args, subFields, …)`) so the parameter order matches `QueryBuilder.AddField` inside sub-field lambdas.
- `dotnet-ngql` global tool — companion CLI that compiles a `QueryBuilder` snippet against `NGql.Core` and prints the rendered GraphQL. Supports rendering from a file or stdin, plus `--execute --endpoint URL` to POST the operation to a live GraphQL server. Mutations are refused unless `--allow-mutations` is passed. Versioned in lockstep with `NGql.Core` and shipped from the same release.

### Changed
- `FieldBuilder.AddField(field, dict, lambda)` — the dictionary at this position is now interpreted as **arguments** (consistent with the rest of the args-first family). In 2.0.0 the same signature was interpreted as **metadata**. Callers that relied on the 2.0 semantic must switch to the four-arg form with the named `metadata:` argument: `b.AddField("user", arguments: null, metadata: dict, action)`. See the migration note inline in `FieldBuilder.cs`.

### Fixed
- `ValueFormatter.AppendString` now escapes embedded `"`, `\`, and control characters per the GraphQL spec (§ 2.9.4). Previously, a string argument like `"hello \"world\""` rendered as `"hello "world""` — invalid GraphQL that most servers rejected.

### Deprecated
- The classic `NGql.Core.Query` and `NGql.Core.Mutation` types are soft-deprecated via XML doc remarks. They continue to work and produce identical GraphQL; new code should prefer `QueryBuilder.CreateDefaultBuilder` and `QueryBuilder.CreateMutationBuilder`. There is no removal timeline.

## [2.0.0] - 2025-12-01

Major release. See [`docs/v2.0.0/RELEASE_NOTES.md`](docs/v2.0.0/RELEASE_NOTES.md) for the full write-up.

### Added
- `PreservationBuilder` — extract a subset of an existing `QueryBuilder` by string path (`Preserve("user.name", …)`) or by typed C# expression (`PreserveFromExpression<T>(x => x.user.email != null)`). Useful for role-based filtering, conditional fragments, and stripping fields from a shared query without rebuilding it.
- `MergingStrategy` enum — `MergeByDefault`, `MergeByFieldPath`, `NeverMerge`. Controls how `Include(otherBuilder)` handles duplicate paths.
- Multi-target support: `net8.0`, `net9.0`, `net10.0`.

### Changed
- Internal rendering and merging path was overhauled for performance: in-place merge in `Include()`, lock-free reads on `FieldChildren`, span-based path parsing, `ArrayPool<T>`-backed argument storage, two-level path-index cache. Query rendering is reflection-free; reflection is confined to the LINQ-expression preservation path.
- `Preserve(...)` moved off `QueryBuilder` onto a dedicated `PreservationBuilder` (call `PreservationBuilder.Create(builder)` to start).

### Removed
- Minimum runtime raised from .NET 6/7 to **.NET 8**.
- `QueryDefinitionExtensions` is now `internal` (was effectively unused outside the assembly).
- `PreserveExtensions` is internal — use `PreservationBuilder` instead.
